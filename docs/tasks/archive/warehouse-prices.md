# Складские товары и выбор минимальной цены

Статус: реализовано; итоговое описание подготовлено к проверке владельцем перед архивированием. Последний зафиксированный локальный прогон — 69 тестов, все прошли. Владелец подтвердил, что складской поток технически работает; полный ручной прогон всех критериев на stage отдельно не зафиксирован.

## Итоговый функционал

Текущее устройство и правила полностью описаны в [архитектуре](../../architecture.md), включая разделы «Складские цены», «Роли и складская отметка», «Цены, каталог, экспорт» и «Проверки и пробелы». Ниже сохранены исходные требования и решения выполненной задачи, а не новая очередь работ.

- Склад обновляется по кнопке вместе с конфигом; при старте используется локальный `warehouse.json`. В памяти и файле хранятся названия и USD-цены строк с остатком > 0, включая ещё не сопоставленные позиции.
- Существующие карточки находятся по `rawNames`; для iPhone нормализуется явно указанный SIM-суффикс. Новые карточки и алиасы не создаются, AI не вызывается.
- Корректные складские предложения участвуют в общем выборе минимальной USD-цены. Снимок заменяет только источник `warehouse`, не удаляя цены поставщиков. Клиентские валюты и правила корзины сохраняются.
- Администратор видит добавленные, удалённые и изменившиеся по цене предложения, а также отдельные списки ненайденных и некорректных строк.
- `manager_retail` и `manager_wholesale` наследуют соответствующие клиентские цены и сценарии; обе роли назначаются `admin`/`superadmin` через добавление или редактирование пользователя, без выдачи менеджерам административных прав.
- Отметку `ITEM_TEXTS.IN_WAREHOUSE` видят менеджеры, `wholesale`, `admin`, `superadmin`; обычный `retail` её не видит. Наличие не зависит от источника минимальной цены. В корзине отметка актуализируется без изменения сохранённой цены.
- `onAiError` и `onUnresolvedItems` используют общий внутренний `sendNamesReport`; пользовательские шаблоны находятся в `ADMIN_TEXTS`. Округление стоимости в `onCostReport` сохранено.

После проверки владельцем этот файл рекомендуется переместить в `docs/tasks/archive/warehouse-prices.md` с исправлением относительных ссылок. Сейчас он не перемещён и не удалён.

## Уточнения, согласованные при реализации

- A — название, C — остаток, D — цена в USD. В обработку передаются только строки C > 0 как массив названий/цен; количество не сохраняется и не ограничивает корзину.
- Google Sheets запрашивается только существующей кнопкой «Обновить конфиг», вместе с ценовыми правилами, цветами и брендами, через `await loadWarehouseFromConfig()`. По дополнительному уточнению владельца склад хранится в отдельном `warehouse.service.ts`: в памяти и `warehouse.json` под `DATA_PATH`, включая ненайденные строки для отчёта. Количества в снимок не входят.
- При старте `loadWarehouseFromFile` читает складской снимок, восстанавливает кеш строк и предложения по текущему кешу товаров без Google и без записи файлов. До первого обновления при отсутствии нового файла используются предложения старого `catalog.json`. Новый файл создаётся при первом обновлении; миграция каталога не нужна.
- Администратору показываются изменения фактически попавших в каталог складских предложений: добавленные, удалённые, старая/новая цена, либо отсутствие изменений. Ненайденные и некорректные строки остаются отдельным отчётом.
- Успешное чтение таблицы — полный снимок складского источника. Исчезнувшие строки, нулевые остатки и строки без корректной цены удаляют прежние складские предложения. Пустой результат очищает только `warehouse`; другие источники сохраняются. Ошибка чтения таблицы сохраняет прежний складской снимок.
- Корректная цена — непустое конечное число > 0. Дубли одного товара сводятся к минимальной цене. Частичные ошибки не мешают корректным строкам; ненайденные и некорректные позиции попадают в отчёт.
- Сопоставление — нормализованное совпадение с существующим `rawNames`, с учётом активации; без AI, догадок об отсутствующих атрибутах и создания товаров. Названия с несовпадающим/отсутствующим SIM либо регионом могут попасть в ненайденные.
- Уточнение 2026-11-18: для складских iPhone после неудачного прямого поиска явно указанный конечный SIM приводится к формату кеша: `Esim` → `(ESIM)`, `Dual Sim` → `(Dual SIM)`, `Sim+esim` → `(SIM + ESIM)`. Используются `normalizeSimByRules` с явным `simTypeRaw` и `buildAAAStoreRawName`. `(Active)` сохраняется. После этого снова выполняется только поиск по `rawNames`; модель, память и цвет не угадываются. Названия AirTag/MacBook не меняются. Нормализованный вариант не записывается в кеш как новый алиас.
- Сохраняются текущие наценки, округления, выбор первого предложения при равенстве, правила корзины и административное отображение цен. Миграция JSON не требуется.

## Цель

Обработать уже получаемые данные складской Google-таблицы,
добавить складские цены существующим товарам каталога
и учитывать их при выборе минимальной цены.

## 1. Обработка складских данных

Использовать существующий механизм получения данных Google-таблицы.
Новый способ загрузки или отдельную интеграцию не создавать.

Реализовать обработку складских строк в существующем потоке импорта.

Для каждого товара:
1. Получить название (колонка A) и складскую цену (колонка D) из существующего формата данных.
2. Найти соответствующий товар в кеше товаров.
3. Для найденного товара подготовить складскую цену (колонка D) для передачи
   в существующий механизм обновления каталога.
4. Для ненайденного товара сохранить название для итогового отчёта
   и продолжить обработку остальных строк.

Ориентир для сопоставления с кешем — ingestAAAStorePrice.
Переиспользовать существующие подходящие механизмы.

Сопоставление выполнять по совпадению названий в соответствии
с существующими правилами проекта.
Не добавлять нечеткий поиск, AI-сопоставление или новые эвристики.

Не создавать новые товары из складских строк, не найденных в кеше.

## 2. Добавление складских цен

Добавить "warehouse" в PriceListType.

Расширить handleIngestResult и связанные типы и обработчики,
чтобы складские цены добавлялись соответствующим товарам каталога.

Складские цены указаны в USD.

Добавление или обновление складского источника не должно удалять
или подменять цены других источников.

Повторная обработка одних и тех же данных не должна создавать
дубли складских предложений.

Поведение при следующих ситуациях должно соответствовать
уже согласованным правилам в документации проекта:
- товар исчез из следующей загрузки складской таблицы;
- остаток равен нулю;
- цена отсутствует или некорректна;
- в таблице есть повторяющиеся строки;
- часть строк обработать невозможно.

Если необходимое правило нигде не зафиксировано, задать только
конкретный недостающий вопрос до реализации соответствующей ветки.

Проверить все места использования PriceListType:
ветвления, отображаемые названия источников, валидацию,
сериализацию и хранение — если они есть в проекте.

## 3. Выбор минимальной цены

Учитывать складские предложения вместе с существующими источниками
при выборе цены товара.

Для сравнения приводить цены к USD с использованием существующего
механизма валютной конвертации и принятых правил округления.

Складская цена уже в USD и не должна повторно конвертироваться
как цена в другой валюте.

Выбирать минимальную цену только среди предложений,
допустимых по существующим правилам актуальности и доступности.

Сохранить существующие правила валюты отображения:
USD для сравнения не означает обязательное отображение в USD.

При одинаковых ценах использовать существующий порядок выбора.
Если такого правила нет и выбор источника влияет на заказ,
уточнить поведение.

Проверить весь связанный путь:
каталог → карточка товара → корзина → сообщение заказа.

Сохранить согласованность выбранной цены, валюты и источника
в соответствии с документированными правилами проекта.
Не менять правила фиксации или пересчёта цен в корзине
без отдельной необходимости и согласования.

Не дублировать алгоритм выбора минимальной цены в разных
обработчиках, если в проекте есть подходящая общая точка.

1. Складские данные обрабатываются через существующую интеграцию.
2. Найденному в кеше товару добавляется источник "warehouse"

9. Цены разных валют сравниваются после корректного приведения к USD.
10. Складская цена не подвергается повторной валютной конвертации.
11. Валюта отображения, источник цены и данные корзины/заказа

## Результат реализации и проверки

- `loadWarehouseFromConfig` использует прежний загрузчик `loadWareHouse` и `saveWarehouse`. Отдельный `warehouse.service.ts` хранит копию строк в памяти и атомарно записывает `warehouse.json`, восстанавливает склад из файла при старте. `ingestWarehousePrices` формирует `IngestResult` без изменения кеша товаров. Общий `replaceCatalogSource` используется сервисом склада и `handleIngestResult`; заменяет только предложения указанного источника.
- `warehouseChangesReport.ts` показывает изменения предложений до/после обновления. `getWarehouseIngestResult` предоставляет ненайденные/некорректные строки из сохранённого снимка для отдельного отчёта. При сбое записи warehouse.json старые память/предложения сохраняются. Транзакции двух файлов нет: если последующая запись производного catalog.json завершилась ошибкой, актуальные предложения восстановятся из warehouse.json на старте.
- Источник `warehouse` поддержан в валютных формулах и отчётах. `getCatalogProducts` выбирает минимум среди конечных положительных исходных и USD-цен. При некорректном RUB-курсе RUB-предложения не участвуют в выборе; порядок равенства сохранён.
- `ProductForCart.source` типизирован как необязательное поле для совместимости со старыми заказами; цена и источник копируются прежними обработчиками корзины, пересчёт не добавлен.
