## Подтверждено владельцем: эксплуатация и бизнес-правила

Сведения ниже получены от владельца после исследования. Подключение к серверам и проверка рабочих данных не выполнялись.

- Prod разворачивается из `main`, stage — из `dev` по необходимости для тестов. Автоматического разворачивания prod нет. Node.js на сервере — 24.13.1. Работает один процесс бота; это не схема параллельного запуска нескольких экземпляров на одном окружении.
- Продакшен обновляется вручную на сервере по схеме README: `pm2 stop aaa-store-bot` → pull ветки `main` → `pnpm run build` → `pm2 start aaa-store-bot`. Здесь зафиксирован порядок владельца, команды агентом не выполнялись. Конкретный текущий commit на серверах неизвестен.
- Рабочий каталог данных на prod — `./data`. Отдельный каталог предложений вне DATA_PATH сейчас не нужен. По сведениям владельца, автоматического резервного копирования JSON, вероятно, нет; он периодически копирует файлы в локальный проект для актуализации данных. Наличие автоматических резервных копий не проверено.
- Наценки из конфигурации — абсолютные суммы, не проценты. RUB — входные цены AAA-store; USD — входные цены второго поставщика, валюта сравнения предложений и оптовые клиентские цены; BYN — розничные клиентские цены. Ко второму прайсу прибавляется 5 USD доставки на товар.
- Точные единицы курсов: `rub_to_usd` — RUB за 1 USD, `rub_to_byn` — BYN за 100 RUB, `usd_to_byn` — BYN за 1 USD. Масштаб курсов подтверждён владельцем и соответствует формулам кода.
- Административные цены без наценки нужны как внутренняя информация. Чтобы назвать клиентскую цену, администратор использует отдельный оптовый либо розничный аккаунт с соответствующей ролью. Это не устраняет отмеченную ниже особенность подписи валюты административных цен.
- Назначение исключения товаров из клиентского каталога — не показывать позиции с проблемной наценкой либо определением бренда/цвета. Это бизнес-намерение; код ниже описан отдельно: неизвестный бренд может отсеиваться при импорте, `hidden` вычисляется по правилам наценок, универсальная проверка неизвестного цвета этим описанием не подтверждается.
- Разные SIM, цвет, регион и статус активации могут различать товары независимо от совпадения цен. Для iPhone принято учитывать региональные различия через тип SIM; отдельное различение регионов при одинаковом SIM сейчас не требуется. По пояснению владельца, нюансы японских моделей (звук затвора камеры) уточняются покупателем или менеджером и не требуют отдельной логики каталога. Это принятое бизнес-правило, а не гарантия корректности каждой текущей ветки сопоставления.
- Определение цвета особенно важно для телефонов и техники Apple: цвет может влиять на цену. Для остальных товаров различия цвета сейчас менее существенны. Это приоритет бизнеса, не указание игнорировать существующие цветовые атрибуты остальных товаров и не подтверждение полноты проверки цвета в коде.
- `ADMIN_CHAT_ID` — Telegram-группа заказов. Заказы предназначены преимущественно для оптовиков; розничным клиентам пока цены называют менеджеры. Это описание практики использования, не подтверждение запрета розничной отправки в коде.
- Складские предложения реализованы; поток описан в разделе «Складские цены». В таблице A — название товара, C — остаток, D — цена в USD. Остаток используется только для отбора строк > 0 и не хранится в каталоге. Складской снимок названий/цен хранится отдельно в памяти и `warehouse.json`, включая ещё не сопоставленные строки. Резервирование и списание не реализованы.
- Интерфейс преимущественно сценарный: пользователь выбирает предусмотренные кнопки, а текст вводит, когда бот запрашивает конкретное значение, например количество товара или курс для администратора. Свободный диалог не является назначением бота. Это уточнение владельца не устанавливает поддержку групповых пользовательских чатов.
- USDT и новый поставщик с входными ценами в USDT, а также курс USDT/USD — будущий план. Текущие типы и формулы эту поддержку не реализуют.
- Фиксацию/пересчёт цены и поведение при неудачной отправке сейчас менять не нужно. Владелец внесёт плановые задачи в Git issues; отдельный список планов в документации не ведётся.
- Конкретные commit на серверах, автоматические резервные копии и поддержка групповых пользовательских чатов остаются непроверенными фактами. Владелец подтвердил, что серверная проверка для текущей документации не требуется.

## Подтверждено кодом: модули и запуск

- `src/index.ts`, `bootstrap`: создаёт бота, загружает пользователей, кеш товаров, каталог, курсы, правила цен, заказы, бренды, цвета и склад через `loadWarehouseFromFile`; регистрирует обработчики, запускает Apple watcher и очистку старых XLSX в `TMP_PATH` с часовым интервалом. Складские предложения в памяти восстанавливаются из `warehouse.json` по текущему кешу товаров. Google Sheets при старте не запрашивается; Apple watcher сохраняет своё прежнее поведение.
- `src/bot.ts`, `createBot`: требует `TELEGRAM_BOT_TOKEN`, удаляет webhook с `drop_pending_updates: true`, запускает polling. Это происходит до загрузки локальных данных и регистрации обработчиков.
- `src/handlers/start.handler.ts`, `message.handler.ts`, `callback.handler.ts`, `document.handler.ts` — входящие события; `src/render/` строит экраны и отчёты, `src/keyboards/` — inline-клавиатуры, `src/texts/` — сообщения.
- `registerMessages` в `src/handlers/message.handler.ts` обрабатывает текст зарегистрированного пользователя: сначала предусмотренные значения глобального меню (`menuHandlers`), затем ввод по текущему `state.mode` (`modeHandlers`). Произвольный текст без соответствующего обработчика не запускает свободный диалог. При несовпадении версии UI возможно отдельное уведомление об обновлении интерфейса.
- `src/services/users.service.ts` — пользователи, роли и проверки `isAllowed`, `isAdmin`, `isSuperAdmin`. В ряде обработчиков идентификатор чата используется как идентификатор пользователя; поддержку групповых пользовательских сценариев нельзя считать проверенной.
- `src/state/chat.state.ts` — `Map<number, ChatState>`, секции, шаги интерфейса и корзина. Начальное состояние клонируется через `structuredClone`; `setChatState` объединяет секции по ключам.

## Подтверждено кодом: роли и складская отметка

Пользовательские тексты хранятся в константах соответствующих файлов `src/texts/*.texts.ts`; новые сообщения, кнопки, ошибки и отчёты следует добавлять туда, включая эмодзи. Динамические шаблоны/функции сообщений также размещаются в `src/texts`. Текст складской отметки — `ITEM_TEXTS.IN_WAREHOUSE` в `src/texts/item.texts.ts`; его используют `getWarehouseMarker` и проверки отображения в тестах.

`src/types/user.ts` содержит роли клиентов, менеджеров и администраторов. Менеджерские роли повторяют пользовательские сценарии соответствующей клиентской роли; административные права им не выдаются. Дополнительные права менеджеров пока ограничены просмотром складской отметки.

| Роль | Цены и валюта | Отметка «📦 На складе» |
| --- | --- | --- |
| `retail` | Розничные, BYN | Нет |
| `manager_retail` | Как `retail`, BYN | Да |
| `wholesale` | Оптовые, USD | Да |
| `manager_wholesale` | Как `wholesale`, USD | Да |
| `admin`, `superadmin` | Исходные цены выбранного предложения, как прежде | Да |

`src/utils/roles.ts`: `getPricingRole` сопоставляет менеджерские роли клиентским для наценок (`priceFormat`, `findPriceRule`), валюты (`getCurrency`), подписей цен и ссылки на менеджера. `canSeeWarehouse` и `getWarehouseMarker` определяют доступ к складской отметке. В сообщениях заказов у менеджеров отдельные читаемые подписи роли (`src/services/orders.service.ts`). Рабочие часы и меню админа для них остаются такими же, как у клиентов.

`getCatalogProducts` добавляет `Product.inWarehouse` только для разрешённых ролей, если среди допустимых предложений есть `warehouse`. Флаг не зависит от выбранного `source`: товар остаётся помеченным и при более выгодной цене другого поставщика. Складские данные показываются в каталоге (`src/utils/message.utils.ts`), выборе товара/количества и корзине (`src/render/renderFlow.ts`). В корзине отметка определяется по текущему каталогу при отображении, сохранённая цена и количество не меняются. Розничному клиенту складская отметка не показывается, в том числе после смены роли со старой корзиной. Дополнительной колонки склада в CSV/XLSX нет.

Назначение `manager_retail` и `manager_wholesale` доступно `admin` и `superadmin` в добавлении и редактировании пользователя. Клавиатуры в `src/handlers/users/addUser.handler.ts` и `editUser.handler.ts` используют общий `getAssignableRoles`. В `src/handlers/callback.handler.ts` сохраняется проверка администратора, дополнительно проверяется допустимость роли (`isAssignableRole`), включая защиту от неизвестной роли или назначения административной роли обычным администратором через поддельный callback. Только `superadmin` видит и назначает административные роли, как предусматривали прежние клавиатуры. Роли сохраняются в существующем поле `User.role` в `users.json`; миграция и изменение пользователей на диске при разработке не выполнялись.

## Подтверждено кодом: импорт и сопоставление

`registerDocumentHandler` в `src/handlers/document.handler.ts` принимает документ от администратора в режиме `upload_xlsx`, скачивает его в `TMP_PATH`, читает Buffer и выбирает импорт по `flowStep`. Обе функции находятся в `src/services/xlsx.service.ts`; большой закомментированный вариант AAA-импорта не является исполняемым поведением.

1. `ingestAAAStorePrice` читает первый лист через `sheet_to_json` с `defval: ""`. Обязательные заголовки: `SKU`, `Категория`, `Название`, `Модель`, `Цена`; дополнительно читаются `Хранилище`, `Страна`, `Тип SIM`. Наличие SKU требуется, но идентификатор кеша создаётся собственной функцией. Пустые название/цена и неизвестный бренд пропускаются. Нормализуются память, цвет, SIM; для не-iPhone регион участвует в сопоставлении и атрибутах. AAA ищет только неактивированные карточки. После поиска по rawName для Apple-смартфонов возможен AI-поиск среди отфильтрованных кандидатов; иначе создаётся карточка. Для остальных товаров есть отдельная ветка создания без AI-матчинга.
2. `ingestTodayThereTomorrowHerePrice` читает первый лист: A — название, B — цена, первая строка пропускается. Обрабатывает смартфоны и распознанные iPhone-аксессуары; другие категории пропускает. Цена округляется до целого, затем добавляется `TODAY_THERE_TOMORROW_HERE_PRICE_DELIVERY = 5`. Из названия извлекаются бренд, флаги, память, цвет, SIM и активация. Сначала поиск по rawName с разделением активированных/неактивированных товаров. Аксессуарам назначается модель по названию без AI извлечения модели телефона. Для остальных вызывается `extractModelOnly`, затем идёт поиск по модели среди кандидатов с совместимыми атрибутами; при отсутствии совпадения создаётся товар. Следующий AI-матчинг в этой ветке закомментирован.
3. Обработка идёт порциями по 15 с `Promise.all`; кеш сохраняется после накопления 100 результатов и в конце. Дедупликация по `rawNameForMatch + "|" + product.id` с выбором меньшей числовой цены действует внутри порции, а не всего файла. Обе функции возвращают `IngestResult`: `items`, `totalRows`, `skipped`, и могут вызывать callbacks отчётов.
4. `handleIngestResult` (экспортирован из `src/handlers/document.handler.ts`) при пустом XLSX-результате сообщает ошибку и не очищает старые предложения. При непустом результате вызывает общий `replaceCatalogSource(source, items)`, сохраняет каталог, отправляет отчёт скрытых товаров и сводку, вызывает `generateRetailCsv`. Параметры позволяют передать `skipped` и отключить отчёт скрытых товаров/CSV. Для источника `warehouse` допускается пустой результат; фактический складской поток теперь работает через отдельный сервис ниже и использует тот же `replaceCatalogSource`. Обработчики XLSX по-прежнему не передают `skipped`.

## Подтверждено кодом: складские цены

Поток данных: кнопка «Обновить конфиг» → `loadWarehouseFromConfig` → `loadWareHouse` → `saveWarehouse` → `ingestWarehousePrices` → `replaceCatalogSource` → сохранение каталога. При старте: `loadCatalog` → загрузка остальных локальных настроек → `loadWarehouseFromFile` → восстановление складских предложений в памяти без Google-запроса.

`loadWarehouseFromConfig` в `src/services/sheets.service.ts` вызывается в `RENEW_PRICE` последовательно с обновлением ценовых правил, брендов и цветов. Внутри `loadWareHouse` получает таблицу через прежний `getSheet`, отбирает C > 0 и возвращает `WarehousePriceRow[]` с названием A и ценой D, затем `saveWarehouse` сохраняет снимок. `ingestWarehousePrices` в `src/services/xlsx.service.ts` нормализует название через `normalizeStorageInName` и ищет его через `findByRawName` с учётом `(Active)`. Если прямого совпадения нет, `normalizeWarehouseSimSuffix` приводит явно указанный SIM в конце названия iPhone к формату кеша: `Esim` → `(ESIM)`, `Dual Sim` → `(Dual SIM)`, `Sim+esim` → `(SIM + ESIM)`. Используются `normalizeSimByRules` с явным `simTypeRaw` и `buildAAAStoreRawName`; `(Active)` сохраняется. Затем повторяется только поиск по `rawNames`. Для остальных товаров эта нормализация не применяется; отсутствующий SIM/регион, модель, память и цвет не угадываются. Ни AI, ни создание карточек, ни добавление алиасов в кеш не используются.

`src/services/warehouse.service.ts`: `getWarehouse` возвращает копию кеша строк; `saveWarehouse` проверяет структуру, атомарно записывает `warehouse.json` через `writeJsonFileAtomic`, обновляет кеш в памяти и производные предложения через `replaceCatalogSource` / `saveCatalog`. `loadWarehouseFromFile` читает локальный снимок и восстанавливает только память и предложения без записи файлов и запросов сети. Если файл ещё не создан, остаются складские предложения старого `catalog.json`; после первого обновления файл создаётся автоматически. При повреждении файла ошибка логируется, каталог остаётся прежним. Миграция существующего каталога не нужна. Атомарной транзакции двух файлов нет: если сохранение производного `catalog.json` не удалось после записи склада, актуальные предложения восстановятся из `warehouse.json` при старте.

Складская цена должна быть непустой, конечной и > 0. Повторы одного productId сводятся к минимальной цене. Успешно прочитанная таблица является полным снимком: прежние `warehouse`-предложения удаляются, затем добавляются корректные найденные строки; исчезнувшие, нулевые остатки, некорректные и ненайденные позиции не сохраняют прежнюю складскую цену. Другие источники не очищаются. Ошибка Google-запроса не заменяет складской снимок. Частичные ошибки строк не мешают корректным позициям. `src/render/warehouseChangesReport.ts`: `takeWarehouseSnapshot`, `buildWarehouseChangesMessages`, `sendWarehouseChangesReport` показывают инициатору обновления добавленные и удалённые предложения, старую/новую цену изменённых и отсутствие изменений. `sendIngestSkippedReport` отдельно отправляет полные списки ненайденных и некорректных строк порциями по лимиту Telegram; результат берётся через `getWarehouseIngestResult`. На складе нет доставки +5 USD второго прайса.

## Подтверждено кодом: кеш и идентичность товаров

`src/services/products/products.service.ts` хранит `Map<id, CachedProduct>`. `findByRawName` сравнивает нормализованные `rawNames`, опционально учитывая активацию. `product.builder.ts` содержит `buildAAAStoreRawName`, `buildTodayThereTomorrowHereRawName`, `addRawNameIfNeeded`, `upsertProduct`. Последний строит ID из структуры и добавляет алиас при совпадении, не заменяя остальные поля существующей карточки. `generateId` в `productId.ts` — первые 12 hex-символов MD5 нормализованных полей; `rawName` влияет только если передан (в `upsertProduct` не передаётся).

Импорт не транзакционный: изменения кеша сохраняются ещё до `handleIngestResult`; атомарной замены пары «кеш + каталог» нет. В одной не-iPhone ветке AAA `isNew: !existingProduct` вычисляется уже после присваивания созданной карточки — счётчик новых товаров не следует считать надёжным без отдельной проверки.

## Подтверждено кодом: цены, каталог, экспорт

В `src/render/reports.ts` отчёты `onAiError` и `onUnresolvedItems` используют общий внутренний `sendNamesReport`: заголовок со счётчиком, список названий, отправка в `ADMIN_ID` и разбиение по `TELEGRAM_MESSAGE_LIMIT`. Шаблоны заголовка и строки — `ADMIN_TEXTS.COUNTED_REPORT_HEADER` и `ADMIN_TEXTS.REPORT_NAME_LINE` в `src/texts/admin.texts.ts`. Пустой список ничего не отправляет. `onCostReport` остаётся одиночным сообщением со стоимостью до четырёх знаков после запятой.

`src/types/product.ts`: `PriceListType = "AAA-store" | "Today there tomorrow here" | "warehouse"`. `CachedProduct` — карточка без цены; `CatalogItem` — `productId` и `offers` с `price: string`, `source`, необязательной `country`. Отдельного поля валюты у предложения нет. `upsertCatalog` обновляет по сочетанию источника и страны; повторные значения перезаписываются, минимум по всем строкам здесь не вычисляется. Складской обработчик выбирает минимум дублей до этого вызова. Схема JSON не менялась, миграция не нужна.

`src/services/catalog/catalog.builder.ts`, `getCatalogProducts`: соединяет каталог с кешем, исключает отсутствующие карточки/предложения, выбирает минимальное предложение после валютной нормализации. Участвуют только конечные положительные исходные и нормализованные цены; RUB при неработающем курсе не участвует. Сравнение без клиентского округления; при равенстве остаётся первое предложение в массиве. Для Apple-смартфонов скрывает страну в представлении. Без роли и для admin/superadmin оставляет исходную цену выбранного предложения; для клиентов вызывает `priceFormat`. Это означает, что административные цены могут иметь разную исходную валюту, хотя `getCurrency` возвращает для администратора `₽` (существующая особенность не менялась).

`src/utils/priceFormat.ts`:

- AAA-store трактуется как RUB; второй прайс и `warehouse` — USD. `normalizeOfferPrice` и `toUsdPrice` делят RUB на `rub_to_usd` для сравнения в USD. Склад не подвергается повторной конвертации; оптовая и розничная формулы для него совпадают с формулами USD-источника.
- `findPriceRule` подбирает правила по категории/бренду/роли, заменяет бренд не-Apple смартфонов на `Android`, отдаёт приоритет совпадениям keywords, затем выбирает порог `max` в USD. Возвращаемый `value` прибавляется как абсолютная сумма в USD, хотя переменные в загрузчике Google-таблицы названы `*Percent`.
- Опт: `(RUB + value * rub_to_usd) / rub_to_usd` либо `USD + value`, округление до целого USD. Розница: `(RUB + value * rub_to_usd) / 100 * rub_to_byn` либо `(USD + value) * usd_to_byn`, округление до десятков BYN.
- `hidden` выставляется, если оба поиска правила (опт/розница) возвращают falsy; нулевая наценка неотличима от отсутствия правила в этой проверке. Начальные курсы при отсутствии/ошибке файла — нули, защита всех вычислений от нулевого делителя не реализована.

`src/services/catalog/ui/catalog.ui.ts`, `getCatalogUIProducts`: исключает `hidden`, фильтрует бренд/категорию/модель/память и сортирует для UI. `getCatalogProductById` берёт данные из общего builder и сам не отбрасывает `hidden`. Шаги каталога строит `src/render/renderFlow.ts`: бренд → категория → модель → память → товар. Callback-значения строятся утилитами; `src/services/callbackHashMap.ts` хранит соответствия хешей в памяти.

`src/handlers/catalog.hanlder.ts` (именно такое имя): `sendPriceList` отправляет XLSX через `src/services/catalog/catalog.export.ts`; `generateRetailCsv` строит розничные видимые товары и пишет CSV. `src/utils/file.service.ts`, `saveCsvToFile`: `products.csv` в `EXPORT_CSV_PATH` либо `/var/data/exports`. XLSX создаются в `TMP_PATH`.

## Подтверждено кодом: корзина и заказ

`src/handlers/callback.handler.ts`: `CHOOSING_PRODUCT` выбирает ID, `CHOOSING_AMOUNT` получает карточку с ценой по роли и добавляет её копию с количеством в `sections[CART].currentOrder`. Повторный ID увеличивает количество существующей позиции; её прежняя цена сохраняется. Есть изменение количества, удаление позиции и очистка корзины. Корзина находится только в памяти и теряется при перезапуске.

`SUBMIT_ORDER` проверяет непустую корзину, вызывает `createOrder` и `addOrder` из `src/services/orders.service.ts`, затем `bot.sendMessage(ADMIN_CHAT_ID, ...)`, затем очищает корзину и показывает подтверждение. `createOrder` фиксирует позиции, сумму, пользователя, статус `new` и ISO-время; `buildOrderMessage` строит HTML. Перед отправкой нет повторного расчёта цен/проверки складских остатков. Заказ сохраняется в JSON до Telegram-отправки: при ошибке отправки он уже существует, а корзина ещё не очищена; отдельной гарантии однократной доставки нет.

Добавление и отправка обёрнуты в `guardWorkingHours` (`src/utils/workingHours.ts`): для неадминистраторов 11:00–20:59 Europe/Minsk; непустой `DEV` снимает временное ограничение. История заказов показывается через `src/handlers/orders.handler.ts`.

## Проверки и пробелы

TypeScript: strict, ES2020, CommonJS, `resolveJsonModule`, `outDir: dist`; include — `src` и `data/**/*`. `scripts/` не входит в эту проверку. `package.json` содержит только `dev`, `build`, `start`; package manager — pnpm@11.5.2. Зависимости включают TypeScript 5.9, ts-node, cpx; точные установленные версии здесь не проверялись.

При исходном исследовании успешно выполнено `node node_modules/typescript/bin/tsc --noEmit` (код выхода 0, без диагностики). Для складской задачи добавлен `tests/warehouse-prices.test.ts`: встроенный `node:test`, запуск `node -r ts-node/register --test tests/warehouse-prices.test.ts`. Тесты проверяют чтение строк Google через заглушку, сопоставление, полные снимки, дубли, сохранение/загрузку формата JSON, выбор и округление цен, отчёты, обновление кнопкой, оба пути добавления в корзину и отправку заказа, регрессии обоих XLSX-импортов. Сеть и файловые записи изолированы; рабочие файлы не читаются. Test/lint scripts и конфигурация линтера отсутствуют. Результаты проверок реализации — в документе складской задачи. Сборка и установка не выполнялись.

После добавления менеджерских ролей выполнено `node -r ts-node/register --test tests/warehouse-prices.test.ts`: 66 тестов, все прошли. Помимо склада покрыты клиентские цены/валюты менеджеров для всех источников, видимость наличия независимо от минимальной цены, отсутствие отметки у `retail`, добавление/редактирование менеджеров от `admin` и `superadmin`, сохранение/загрузка ролей, ограничения поддельных callback, экраны товара/корзины без изменения сохранённой цены, ссылки на менеджеров и подписи ролей в заказах. `node node_modules/typescript/bin/tsc --noEmit` прошёл; `git diff --check` без ошибок (Git сообщает предупреждения о CRLF в части файлов). Линтер, сборка, реальный бот и внешние сервисы не запускались. Ручная проверка новых ролей в Telegram не выполнялась. Для неё на stage нужно назначить обе роли через добавление и редактирование, сравнить цены с клиентскими аккаунтами и складские отметки с `retail`/`wholesale`, затем удалить складское предложение и проверить исчезновение отметки в корзине.

Не проверены исполнением: форматы реальных XLSX, AI-качество сопоставления, формулы на рабочих курсах, повторный импорт и конкурирующие импорты, перезапуск/восстановление JSON, отказ Telegram при отправке, права Google API, схема склада и деплой. Для будущих тестов можно использовать небольшие искусственные или обезличенные XLSX-примеры: они позволяют проверить заголовки, сопоставление и цены без настоящих коммерческих данных. Сейчас предоставлять файлы не требуется. Для исполнения тестов также нужны изолированные пути и заглушки сети; существующие импортеры нельзя считать чистыми функциями без записи и сети.

Добавлены проверки пустого списка, заголовков, состава и порядка названий, адресата, разбиения списочных отчётов и округления стоимости. `node node_modules/typescript/bin/tsc --noEmit` и `git diff --check` также прошли; реальные сообщения Telegram не отправлялись.
